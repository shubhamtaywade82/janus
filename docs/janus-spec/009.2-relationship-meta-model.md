## 1. Core Philosophy: Relationships as Entities
In the Janus Temporal Knowledge Operating System (TKOS), a Relationship (Edge) is not just a static label in a graph; it is a **first-class domain entity**. 
A relationship has its own identifier, lifecycle, weight, confidence level, supporting evidence, and provenance. This allows relationships to evolve dynamically as new market data prints, without requiring any modifications to the underlying nodes (Market Objects).

---

## 2. The Relationship Schema

Every relationship entity in the Janus graph must implement this contract:

```typescript
export interface MarketRelationship {
  // --- IDENTIFICATION ---
  id: RelationshipId;               // UUID v7 (Time-sortable)
  kind: RelationshipType;           // Enum: 'SWEEPS', 'FILLS', 'CONTAINS'
  family: RelationshipFamily;       // Enum: 'STRUCTURAL', 'TEMPORAL', 'CAUSAL'
  
  // --- ROUTING ---
  sourceId: MarketObjectId;         // Source node ID
  targetId: MarketObjectId;         // Target node ID
  directionality: 'DIRECTED' | 'UNDIRECTED' | 'BIDIRECTIONAL';
  cardinality: 'ONE_TO_ONE' | 'ONE_TO_MANY' | 'MANY_TO_MANY';
  
  // --- TEMPORAL & LIFECYCLE ---
  state: RelationshipState;         // Enum: 'FORMING', 'ACTIVE', 'RESOLVED'
  createdAt: ExchangeTime;          // Exchange timestamp when formed
  updatedAt: ExchangeTime;          // Last update of weights/confidence
  resolvedAt?: ExchangeTime;        // Terminal timestamp
  
  // --- QUANTITATIVE METRICS ---
  strength: number;                 // 0.0 to 1.0 (Geometric or physical overlap weight)
  confidence: number;               // 0.0 to 1.0 (Probability of structural validity)
  
  // --- EVIDENCE & AUDITABILITY ---
  evidence: {
    interactions: string[];         // Parent MarketInteraction IDs
    metrics: Record<string, number>;// Supporting metrics (e.g. RVOL, DeltaImbalance)
  };
  provenance: {
    system: string;                 // System that built the edge (e.g., 'CausalRelationSystem')
    ruleVersion: string;            // Version of the projection rule
  };
}
```

## 3. Orthogonal Meta-Model Dimensions

Relationships are classified and handled by the engine using these dimensions:

| Dimension | Purpose | Allowed Values |
| :--- | :--- | :--- |
| **Decay Model** | How does the relationship weaken over time? | `EXPONENTIAL_DECAY`, `STEP_FUNCTION`, `PERSISTENT` |
| **Evidence Model**| What is required to justify this edge? | `INTERACTION_DRIVEN`, `MATHEMATICAL`, `AI_INFERRED` |
| **State Evolution**| Can the relationship transition states? | `MUTABLE`, `IMMUTABLE` |

---

## 4. Derived System Capabilities

Capabilities are derived mechanically from the Relationship Meta-Model:
- If `decay_model == EXPONENTIAL_DECAY` $\rightarrow$ Projector applies `lambda` decay factor on every candle close.
- If `evidence_model == INTERACTION_DRIVEN` $\rightarrow$ Edge requires at least one verified `MarketInteraction` event in its transaction logs.
- If `state_evolution == MUTABLE` $\rightarrow$ The `RelationshipSystem` can update the weight/confidence dynamically.
