## 1. Core Philosophy: The Semantic Bridge
While **Facets** describe the intrinsic, objective properties that an object *has*, **Affordances** describe what the object *offers* to a trading thesis. 

Affordances act as the strategy-neutral interface between raw market structure and trade execution. They represent the vocabulary that the Strategy Engine, Policy Engine, and AI Brain use to build, communicate, and govern trade ideas.

```
┌─────────────────┐       ┌──────────────────┐       ┌────────────────────┐
│ Market Object   │ ─────>│ Facets           │ ─────>│ Affordances        │
│ (Entity: Fact)  │       │ (Data: Physical) │       │ (System Utility)   │
└─────────────────┘       └──────────────────┘       └─────────┬──────────┘
                                                               │
                                                               ▼
                                                     ┌────────────────────┐
                                                     │ Trade Setup        │
                                                     │ (Composition)      │
                                                     └────────────────────┘
```

## 2. The Affordance Registry

The Janus runtime organizes trading decisions around a standardized set of affordances:

### 2.1 `Entry` Affordance
Allows a localized price zone to trigger trade execution.
- **Physical Requirements**: Geometry: `ZONE` or `CURVE`, Execution: `TRADABLE`.
- **System Actions**: The Execution Engine calculates entry order distributions (e.g. limit ladders) within the boundary of this affordance.
- **Examples**: `FairValueGap`, `OrderBlock`, `VWAPAnchor`.

### 2.2 `Target` Affordance
Provides a logical destination where price is mathematically expected to travel.
- **Physical Requirements**: Geometry: `ZONE`, `RANGE` or `POINT`, Execution: `TARGETABLE`.
- **System Actions**: The Strategy Engine verifies Risk-to-Reward (R:R) by measuring the distance between the `Entry` affordance and the `Target` affordance. The Execution Engine maps take-profit orders here.
- **Examples**: `LiquidityPool`, `HighVolumeNode`, `EqualHighs`.

### 2.3 `Invalidation` Affordance
Defines the boundary where the structural logic of the trade is broken.
- **Physical Requirements**: Geometry: `POINT` or `RANGE`.
- **System Actions**: If price trades beyond this boundary, the `TradeWorkflow` is forcefully aborted or stopped out.
- **Examples**: `SwingLow` (for Longs), `BreakerBlock` opposite boundary.

### 2.4 `Confluence` Affordance
Serves to confirm or amplify the score of another primary affordance.
- **Physical Requirements**: Any geometry.
- **System Actions**: The Scoring System matches overlaps (confluences) between a primary `Entry` affordance and secondary `Confluence` affordances to scale position size.
- **Examples**: `FibonacciRetracement`, `VolumeShelf`, `FundingZScore`.

### 2.5 `Context` Affordance
Provides high-level environment constraints or bias.
- **Physical Requirements**: Lifecycle: `CONTINUOUS` or `EPISODIC`.
- **System Actions**: Filters out lower-timeframe setups that oppose the context direction.
- **Examples**: `TrendBias`, `VolatilityRegime`, `ActiveSession`.

## 3. Strategy Composition via Affordances

By designing the system around affordances, Janus strategies become modular. A strategy does not hardcode object types; it specifies a **Composition Blueprint**.

### Example: Imbalance Trend Reversal Setup
```yaml
strategy:
  name: ImbalanceTrendReversal
  blueprint:
    context:
      affordance: Context
      requirements: { direction: BULLISH }
    setup:
      trigger: Sweep
      entry:
        affordance: Entry
        requirements: { domain: IMBALANCE, state: ACTIVE }
      stop:
        affordance: Invalidation
        requirements: { domain: STRUCTURE }
      target:
        affordance: Target
        requirements: { domain: LIQUIDITY }
```

When this strategy runs, it queries the graph:
1. "Does the active `Trend` (Context) equal BULLISH?"
2. "Has a `LiquiditySweep` (Sweep) occurred?"
3. "Find all active `Imbalances` offering `Entry` (returns FVGs and OBs)."
4. "Find nearest `Structure` offering `Invalidation` (returns Swing Low)."
5. "Find nearest `Liquidity` offering `Target` (returns Liquidity Pool)."

The strategy calculates risk and initiates execution. If we introduce a new object type to the ontology tomorrow (e.g. `SpoofingDeltaZone`) and tag it with the `Entry` affordance, this strategy can immediately trade it without any logic updates.
